# Castra 0.3.0

Status: prepared locally, not published. All six `@castra-kit/*` packages use 0.3.0.

## Release notes

Remote MCP audit rows now mask payload values, including rejected calls and write attempts. Optional
`audit.redactKeys` hides whole subtrees and `audit.retentionDays` prunes one bounded batch after auditing.
Existing rows are unchanged; operators should explicitly prune historical sensitive arguments. Retention
is disabled by default and its failures do not alter served results. No database migration is needed.

`castra rollback` activates a previous Worker version only after checking live D1 schema and config
fingerprints recorded by `castra deploy`. It supports dry-run and explicit version selection, requires
Worker-name confirmation, and rechecks state before activation. Older unmarked/secret-only versions,
schema/config mismatch, split traffic and multiple D1 bindings are refused. It does not restore data,
reverse migration effects or force Cloudflare resource/secret refusals. The scaffolder adds a rollback script.

Upgrade from 0.2.1: [generated guide](../upgrading/0.3.0.md). From 0.1.x, apply the 0.2 wiring migration first.
MCP migration tools (#20), R2 routes, bulk operations and multi-tenancy remain outside this release.

## Verification

Lint, build, typecheck, full tests (1288 passed; 7 opt-in tests skipped), 529 policy tests, generated upgrade
note checks and the actual 0.2.1 -> 0.3.0 upgrade test (2 passed) all passed. Policy tests overlap the full suite.
All six pnpm tarballs were inspected: versions/dependencies are 0.3.0, runtime entries exist, no local
rollback test files or environment secrets are included. The create package includes the rollback script.

On the isolated example Worker/D1, successful rollback and config mismatch refusal were verified. A live
schema probe was refused, removed, and original/final SQLite DDL matched; active deployment stayed unchanged.
See [PROGRESS](../PROGRESS.md) for evidence and the distinction from the consumer production API.

## Publication steps

1. Merge the reviewed release commits and require the GitHub CI job to pass on the final commit.
2. Publish all six packages together using the repository's `pnpm -r publish` procedure; verify every registry
   version before tagging. If publication is partial, finish missing packages before announcing the release.
3. Tag the final commit `v0.3.0` and create the GitHub release with the release notes above.
4. Mark this changelog/version and the upgrade guide as published, update README/current-state/limits,
   then upgrade and smoke-test the consumer API as a separate deployment.

Local test files and the running example deployment are retained. npm publication, remote branch updates,
tag creation, GitHub releases and the consumer API upgrade have not been performed in this preparation.
