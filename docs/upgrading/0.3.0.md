# Upgrading to 0.3.0

Publication pending. Follow the commands below after 0.3.0 is published. From 0.1.x, first apply the
[0.2.0 wiring migration](0.2.0.md), then this guide. No database migration or new binding is required.

## Audit behavior

New remote MCP audit arguments retain structure but mask all scalar values. Raw payload values are no longer
available in audit rows, including denied calls and write attempts. Existing rows are unchanged and may contain
sensitive data; prune them explicitly with `pnpm exec castra mcp audit prune --older-than 30 --remote` if appropriate.

Optionally configure the packaged app:

```ts
mcp: { audit: { redactKeys: ["password", "token"], retentionDays: 30 } },
```

`redactKeys` masks matching whole subtrees, case-insensitively. Retention is disabled by default. When enabled,
known-token MCP requests prune at most 5000 old rows after durable auditing; idle apps need manual/Cron cleanup.
Retention errors do not undo served results; audit insertion still fails closed before writes.

## Worker rollback

Use `castra deploy` for new deployments. It records live schema/config fingerprints in the version message;
old unmarked and secret-only versions cannot be rollback targets. Deploy two compatible versions before the
first rollback. Use `pnpm exec castra rollback --dry-run` to check the previous deployment, or specify a target
with `--version <UUID>`. Execution prompts for the Worker name, or accepts `--confirm <worker-name>`.

Rollback changes Worker traffic only; D1 row data and migration effects stay as they are. It requires exactly
one provisioned D1, single-version 100% traffic, matching local/current/target configs and a target schema
matching live D1 (including index/trigger DDL). Serialize deploy/migration/rollback operations. Cloudflare
resource or changed-secret refusals are never forced. Local source files remain at their current revision.

This release does not add MCP migration tools, R2 routes, bulk operations or multi-tenancy.
