# Upgrading to 0.4.0

<!-- upgrade-from: v0.3.0 -->

No database migration or new binding is required. From 0.2.x, first apply the
[0.3.0 upgrade](0.3.0.md). From 0.1.x, apply [0.2.0](0.2.0.md) and then [0.3.0](0.3.0.md) first.

## Local MCP migration tools

`castra mcp` now exposes two new tools for the stdio transport (local only — the remote `/mcp` route
does **not** register them):

- `generate_migration { name }` writes the next numbered migration file (`<migrations_dir>/NNNN_<slug>.sql`)
  with a comment-header template and returns the path plus the file body as a preview. The agent fills the
  SQL by hand. Refusals: empty name (MCP SDK protocol-level input validation), whitespace slug → 400
  `invalid_name`, missing wrangler config → 400 `wrangler_config_not_found`, no D1 binding or multi-binding
  without `--binding` → 400 `no_d1_binding`, `migrations_pattern` layout → 400 `migrations_pattern_unsupported`.
- `apply_migration { approve }` runs `migrateStatus` always. Without `approve: true` it returns the dry-run
  summary (`applied`, `pending`, `unknown`) and stops. With `approve: true` it runs the drift check
  (`castra generate --check`) and, only on success, shells out to `wrangler d1 migrations apply` against the
  local D1. Wrangler stdout is silenced so it cannot leak into the MCP JSON-RPC stream. Drift or wrangler
  non-zero exit is reported verbatim and the apply stops.

Both tools are option-gated: the CLI registers them, the remote `/mcp` does not. No new audit code; if a
remote version is ever added, it must register in `WRITE_TOOLS` and `TOOL_SCOPES` and emit an `attempt` row
through `access.beforeWrite`.

`packages.json` scripts do not change. After upgrading, restart `castra mcp`.
